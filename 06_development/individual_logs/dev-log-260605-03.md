* **06.03 - 모듈 공용 부피측정 인터페이스 펑션 모듈 구현 및 임시 테스트 툴 개발**
    * SD 모듈의 `SAPMZB1SD0001` 출고 관리 프로그램과 PP 모듈의 `SAPMZB1PP0005` 생산 계획 및 입출고 제어 프로그램에서 공용으로 연동하여 호출할 부피 측정 펑션 모듈인 `ZFB1CM0002`를 신규 생성하였다.
    * **범용성 확보를 위한 동적 필드 할당 (ANY TABLE & FIELD-SYMBOL):** 협업 모듈마다 펑션 파라미터로 던져주는 인터널 테이블(`IT_TABLE`)의 데이터 구조(PP 생산: `PLPR`, MM 구매: `EBELN`, SD 판매: `VBELN_VA`)가 전부 상이한 환경이었다. 이에 고정된 스트럭처 타입 선언 방식 대신 `ANY TABLE` 규격으로 동적 선언하였으며, `FIELD-SYMBOL`을 정의하여 어떠한 인터페이스 테이블 구조가 유입되더라도 유연하게 파싱할 수 있도록 범용성을 확보하였다.
    * **온도·밀도 보정 및 계절별 랜덤 처리 로직:** 외부 호출부에서 온도(`I_ZTEMP`)와 밀도(`I_ZDENS`) 수치를 인풋 파라미터로 직접 전달할 경우 이를 최선순위 데이터로 인식하도록 제어하였으며, 해당 물리 값들을 결합하여 VCF 보정계수 마스터 테이블인 `ZTB1MM0018`에서 매칭 레코드를 찾아 조회하도록 로직을 구현하였다.
    * **핵심 분기 파라미터 제어 (I_CALTY):** 입력된 기준 수량이 어떠한 명세냐에 따라 연산 방향을 정밀하게 피벗(Pivot)하도록 설계하였다. `I_CALTY` 파라미터 값이 공란(Default)으로 인입될 경우에는 사용자가 입력한 값을 '환산 부피(`ZSVOL`)' 데이터로 인식하여 실측 부피를 역산(입력값 / VCF) 처리하도록 분기하였고, 반대로 `I_CALTY = 'X'`로 인입될 때에는 입력값을 '실측 부피(`ZAVOL`)' 데이터로 간주하여 환산 부피를 계산(입력값 * VCF)하도록 정밀 분기 로직을 성립하였다.
    * **임시 테스트 프로그램(ZMEMO_B08)을 통한 정합성 검증:** 펑션 내부 연산의 완벽성을 기하기 위하여 임시 실행 레포트 프로그램인 `ZMEMO_B08`을 별도 작성하였다. 가상의 하드코딩된 SD 출고 구조 데이터(`ztb1sd0009` 타입)와 PP 자재 이동 데이터(`ztb1mm0012` 타입)를 인터널 테이블에 강제 할당한 뒤, 순차적으로 `ZFB1CM0002` 펑션을 런타임 호출하여 `sy-subrc` 예외 분기 처리를 철저하게 검증하였다. 결과적으로 데이터셋이 올바르게 적재되었을 때, 동일 일자의 참조 문서 세트에 대해 고유 측정 번호(`MSYYMMDDXX`)가 순번대로 자동 증가 및 동기화되며 `ZTB1MM0020` 물리 데이터베이스 테이블에 일괄 `INSERT` 트랜잭션이 완벽하게 성공하는 것을 확인하였다.
* **06.04 – 실제 SD 프로그램, PP 프로그램에서 호출하여 최종 테스트 및 최종 수정**

    * 이에 펑션 모듈 내부 엔진에서 `LFIMG` 필드만 고정적으로 인터셉트하여 읽도록 선언되어 있던 탐색 아키텍처를 전면 수정하였으며, `KWMENG` 필드 내역도 동적으로 추적하여 정상 바인딩할 수 있도록 인터널 테이블 루프 탐색 순서 로직을 완벽하게 재정비하였다.
    * 로직 수정 완료 후 2차 교차 테스트를 진행하던 중, SD 단에서 화면용 테이블(`gt_lips`) 대신 실제 DB 딕셔너리 구조(`ztb1sd0009` 타입)의 로컬 인터널 테이블을 파라미터로 넘겨 바인딩했을 때, 해당 구조체 내부에는 반대로 `KWMENG` 필드가 물리적으로 존재하지 않아 다시금 수량 데이터 누락 오류를 발생하는 연쇄 결함이 나타났다. 이에 타 모듈 담당자와의 긴급 인터페이스 협의를 주도하여, 펑션 호출 시점에는 주문 수량이 확실하게 보장되어 소스 내에서 유연한 파싱이 가능한 화면용 테이블(`gt_lips`) 구조를 파라미터 `IT_TABLE`에 인입하기로 규칙을 전면 통일화하였다.

        * **controller:** `Main.controller.js` 스크립트 파일 내 `onInit` 생성 시점에 세계 지도의 기본 중앙 정렬 좌표(위도 `25.0`, 경도 `-20.0`) 수치와 초기 줌 레벨(`2.5`) 속성이 부여된 `map` 모델을 빌드하였으며, 구체적인 원산지 글로벌 위경도 명세가 담긴 `data` 모델을 뷰 레이어에 바인딩하였다.
        * **view:** `Main.view.xml` 템플릿 단에 `mdcgm:Geomap` 태그 인스턴스를 선언하고 내부적으로 `zpb1mm01/delegate/JSONGeomapDelegate` 중계 객체를 동적 호출하도록 선언하였으며, `features` 파라미터 매핑을 통하여 세계 지도 레이어 위에 오렌지색 데이터 점(color: `'#FFA500'`)들이 정상 렌더링되도록 스크립트를 빌드하였다.
        * **delegate 폴더 (총 2개 파일 생성 및 수정):** `JSONBaseDelegate.js` 파일을 통하여 핵심 타입 맵과의 데이터 중계 인터페이스를 구축하였고, `JSONGeomapDelegate.js` 스크립트를 구현하여 지도의 타일 프로바이더 주소 명세를 앞서 구축한 `osm.json`으로 강제 밀어줌과 동시에, 화면상에 면과 선 오브젝트를 동적으로 그릴 때 필요로 하는 내부 템플릿 인스턴스를 정상 할당하였다.
        * **model 폴더 하위 (총 2개 폴더, 6개 파일 생성 및 수정):** 미국, 사우디아라비아, 멕시코 등 전사 원유 수입의 주요 거점 국가들의 포인트 좌표 명세로 `model/geojson.json` 공간 데이터를 전면 변경하였다. 이와 더불어 지도가 파싱해야 하는 고유 데이터 속성을 정의한 `PropertyInfo.js`, GeoMap 컨트롤과 로우 데이터 간의 유연한 형 변환을 담당하는 `TypeMap.js`, GeoJSON 규격의 공간 영역 형식을 완벽히 인지하는 `Geometry.js`, 프로퍼티 구조를 UI5 데이터 모델에 정합성 있게 바인딩하는 `Feature.js`, 그리고 마지막으로 지도 그래픽상에서 유입 선박의 이동 운항 거리 등을 연산하기 위한 미터 단위 명세서인 `LengthMeter.js` 파일을 순차적으로 완편하였다.
    * 그러나 공식 샘플 구조에 발맞춰 완벽하게 파일들을 배치하고 데이터를 바인딩했음에도 불구하고, 로컬 가상 서버 런타임 환경에서 `sap/ui/geomap/library.js` 코어 파일을 정상적으로 로드하지 못하고 누락되는 `404 (Not Found)` 예외 오류가 콘솔 창에 지속 발생하였다. 
    * 원인을 정밀 추적한 결과, GeoMap 컨트롤은 연동해야 하는 컴포넌트 정보와 종속 파일 구조가 지나치게 방대하며, 로컬 샌드박스 개발 환경 상에서 표준 라이브러리 소스 로드 주소나 외부 지도 API 접근 권한 프로토콜이 단 하나만 미매칭되어도 화면 렌더링 전체가 먹통이 되는 치명적인 인프라 리스크가 잔존함을 식별하였다.
    * 이에 개발 마감 효율성과 런타임 안정성을 전반적으로 고려하여, 물리 구조가 복잡하고 외부 에러 리스크가 큰 GeoMap 컴포넌트를 과감히 배제하고, 구현 방식이 명료하면서 외부 종속성 라이브러리 에러 리스크가 원천 차단된 `AnalyticMap` 오브젝트로 컴포넌트를 선회 채택하여 화면 레이아웃을 정합성 있게 다시 구현하기로 확정하였다.

## 2. 발생한 기술적 오류 및 조치

- **오류 14**: PDF 파일 변환 처리를 위해 사용자 PC의 내부 환경변수(`TEMP`) 경로를 조회하여 스트리밍하는 과정에서, SAP GUI 내부 보안 정책 프레임워크와 충돌하여 '보안 경고' 안내 창이 중복으로 발생하였고, 이에 당황한 현업 유저가 `Deny(거부)` 버튼을 선택했을 때 도리어 불일치하는 엉뚱한 로컬 임시 파일 경로가 강제 생성되면서 파일 오프닝이 완전히 터져버리는 런타임 에러가 발생하였다.
- **조치 14**: 매번 클라이언트 PC의 개별 윈도우 환경 변수를 임의로 조회하는 불안정한 백그라운드 추적 방식 대신, 표준 로컬 다이얼로그 펑션인 `file_save_dialog` 메서드를 소스에 명시적으로 인입하였다. 유저가 다이얼로그 창을 통해 직접 지정하고 선택한 안전한 로컬 물리 저장 경로 데이터만을 파라미터로 명확하게 전달받아 PDF 변환 공정을 태우도록 아키텍처 구조를 안전하게 변경하여 보안 경고 및 오프닝 결함을 해결하였다.

- **오류 15**: 송장 검증 데이터 적재 프로세스를 태우는 과정에서, 화면 헤더 단의 외화 총액 수치와 하단 아이템 단의 원화 총합 데이터 간의 금액 밸런스 정합성이 올바르게 일치하지 않아 저장이 통째로 거부되는 심각한 비즈니스 밸런스 검증 오류가 발견되었다.
- **조치 15**: 연관 트랜잭션 라인을 추적 디버깅한 결과, 본 프로그램의 선행 프로세스 영역인 '서비스 PO 아이템 생성' 로직 단에서 백엔드 데이터베이스로 원화 금액 데이터를 밀어 넣을 때, 실제 금액보다 수치상으로 내부 버퍼가 100배 부풀려진 상태로 잘못 적재되고 있었음을 찾아내었다. 이에 본 송장 검증 프로그램의 유효성 검증 구조는 표준 가이드에 맞게 설계되었으므로 기존 틀을 유지하되, 서비스 PO 개발 담당 멤버에게 송장 유입 전 원천 데이터가 정상 원화 포맷 레코드로 인서트될 수 있도록 `CURRENCY_AMOUNT_IDOC_TO_SAP` 함수를 적용한 마스터 저장 소스 코드 수정을 긴급 요청하여 정합성을 정상화하였다.

- **오류 16**: 헤더 금액과 아이템 금액 간의 미세 차이 수치(`lv_compare`)를 연산하는 과정에서, 소수점 이하 자리 명세가 그대로 살아있는 아이템 정수 누적액 변수와 변환 펑션을 거쳐 소수점 포맷이 `.00` 형태로 완벽하게 닫힌 헤더 데이터 변수 간의 타입 자릿수 불일치 현상이 발생하였고, 이로 인해 SAP 컴파일러가 강제로 임의의 `P(8,0)` 타입으로 가정한 채 연산 처리를 감행하여 시스템 경고 메시지를 지속적으로 출력하는 결함이 인지되었다.
- **조치 16**: 연산 처리를 담당하는 내부 핵심 변수(`lv_compare`, `lv_rounded_item`)의 테크니컬 타입을 천억 단위 이상의 거대 회계 금액 데이터까지 유연하게 수용할 수 있는 `p LENGTH 13 DECIMALS 2` 규격으로 데이터 사양을 명시적 선언해 주어 내부 묵시적 컴파일러 변환 경고를 완벽하게 제거하였다. 더불어 아이템 총 누적액을 연산하기 전 ABAP 내장 함수인 `round(dec = 0)` 구문으로 소수점을 정수 형태로 깔끔하게 반올림 처리하여 1차 정돈한 뒤, 헤더 변수와 깨끗한 정수 상태로 대조 및 오차 자동 보정($\pm 2$원) 로직이 수행되도록 소스코드를 보완하였다.

- **오류 17**: Fiori 애플리케이션 플랫폼 연동을 목적으로 백엔드 영역의 Core Data Service(CDS) 뷰 인프라를 OData 서비스 통신 레이어로 노출 및 등록하는 과정에서, 시스템이 `Parameter has no data element` 정합성 메시지를 호출하며 게이트웨이 서비스 빌드를 전면 거부하는 결함에 직면하였다.
- **조치 17**: 소스 코드를 분석한 결과, CDS 뷰 내부 인터페이스 파라미터 선언부에 사양이 구체화되지 않은 단순 abap 내장 원시 타입(`abap.dats`)으로 속성이 고정되어 있어, 외부 게이트웨이 웹 통신 프로토콜 정의 시 매핑 규격이 모호해진다는 이유였다. 이에 SAP 데이터 사전(Dictionary) 시스템 상에서 구체적인 시스템 사양과 비즈니스 도메인이 정의되어 있는 검증된 표준 데이터 엘리먼트 타입(`zeb1_mm_bldat`)으로 파라미터 타입을 변경 및 재빌드하여 인터페이스 빌드 오류를 처리하였다.

- **오류 18**: 외화 환율 데이터 테이블 연동 및 조인을 처리하기 위하여 내부적으로 `max(b.ukurs)` 집계 펑션과 광범위한 `GROUP BY` 구문이 집약되어 설계된 기존 `zcds_b1_mm_0001` 마스터 CDS 뷰를 SAP SEGW 프로젝트 상에서 OData 서비스 데이터 모델로 직접 매핑하려고 하자, 프로토콜 구조 구조상 호환성 에러를 뿜으며 연동이 차단되는 현상이 식별되었다.
- **조치 18**: 집계 함수와 그룹화 연산이 포함된 하부 데이터 모델 뷰를 웹 통신 인터페이스 레이어에 다이렉트로 결합할 수 없는 게이트웨이 표준 제약을 확인하였다. 이에 해당 `zcds_b1_mm_0001` 뷰 아키텍처를 추상화 단계로 한 번 더 부드럽게 감싸주는 Consumption View인 `zcds_b1_mm_0004`를 딕셔너리에 상위 빌드해 주었으며, 이 래퍼(Wrapper) 뷰를 매개체로 OData 서비스를 연동하여 모델 활성화를 완벽하게 수행하였다.

- **오류 19**: SAP Gateway 외부 CRUD API 테스트 세션 환경에서 `UPDATE_ENTITY(PUT)` 프로토콜 메서드를 요청하였을 때, HTTP 통신 상태 코드는 `204/200 (Success)`으로 정상 반환되지만 실제 백엔드 데이터베이스 테이블 레코드와 우측 응답 결과 데이터 필드 창(`<d:Zsel/>`)에는 가변 데이터가 반영되지 않은 채 공백(Blank)으로 초기화되어 반환되는 데이터 반영 누락 결함이 발견되었다.
- **조치 19**: `DPC_EXT` 클래스 내부의 업데이트 처리 로직 단을 라인 디버깅한 결과, `read_entry_data` 메서드를 정상 가동하여 파싱해 온 프론트엔드의 최신 요청 데이터 구조체(`ls_entity`) 인스턴스를 기존 데이터베이스에서 서칭해 온 타깃 레코드 구조체(`ls_data`)에 덮어쓰는 핵심 명령어인 `MOVE-CORRESPONDING` 구문이 누락되어 있었음을 포착하였다. 이로 인해 과거 데이터셋이 그대로 테이블에 재업데이트 처리가 되고 있었던 오류였으며, `UPDATE_ENTITY` 메서드 내 DB 레코드 존재 유무 검증 로직 직후 `MOVE-CORRESPONDING ls_entity TO ls_data.` 구문을 정확히 추가 삽입하여 사용자가 요청한 가변 데이터(`ZSEL = 'X'`)가 정상적으로 복사 및 교체되어 커밋되도록 결함을 완벽하게 수정하였다.

- **오류 20**: Fiori 프리스타일 프론트엔드 프로그램 구현 도중, 공식 가이드 배치를 준수하여 코드를 구성했음에도 화면상에 `Geomap` 컨트롤 레이아웃이 지속적으로 뜨지 않고 하얗게 번지는 화면 먹통 현상이 발생하였다.
- **조치 20**: 브라우저 F12 개발자 도구 디버깅 창을 통해 네트워크 스트리밍 로그를 정밀 분석한 결과, 웹 애플리케이션 코어 단에서 `sap.ui.geomap` 라이브러리 파일 자체를 외부 주소로부터 핸들링하여 불러오지 못하는 `404 (Not Found)` 웹 에러가 발생하고 있음을 확인하였다. 브라우저 주소창에 `http://localhost:8080/resources/sap/ui/geomap/library.js` 인프라 경로를 다이렉트로 대조 입력해 보아도 아무런 스크립트 소스가 로드되지 않는 상태였다. 이는 현재 가동 중인 가상 로컬 개발 서버의 컨테이너 환경 내에 해당 코어 맵 라이브러리 소스가 패키징되어 포함되어 있지 않거나 외부 방화벽 API 권한 매핑이 일치하지 않아 나타나는 완전한 로컬 인프라 구성 결함으로 분석되었다. 이에 마감 일정을 고려하여 무리한 로컬 서버 환경 변경 대신, 구현 방식이 직관적이며 프레임워크 라이브러리 로드 오류 리스크가 원천 차단된 `AnalyticMap`으로 컴포넌트를 선회 채택하여 결함을 우회 해결하였다.
